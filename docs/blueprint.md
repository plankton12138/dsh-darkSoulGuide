## 0. 一句话定位

**通用攻略回答「这游戏怎么打」，本插件回答「你接下来该干什么」。**

需要三样东西叠在一起：你的存档状态、游戏的因果结构（打谁开哪扇门）、你的个人目标。缺一样就退化成普通攻略。

**当前状态：可用的最小闭环。** 三个工具、六个数据切片，已在 DSH 里跑通并读出了真实进度。

## 1. 分层

```
   DS30000.sl2  (BND4 · AES-128-CBC · 12 条目)
          │ ① 解密 + 去长度前缀
          ▼
   tools/ds3/dump_save.py        ← 唯一会崩的地方
   容器解析 · 角色定位 · 旗标解码 · 背包/装备扫描
          │ ② JSON（GameState 形状）
          ▼
   src/parsers/ds3/run.js
   找 Python · 跑子进程 · 错误分类 · 5 秒缓存
          │ ③
          ▼
   src/tools/ds3.js               ← 三个模型工具
   src/state/route.js             ← 连通图寻路
          │ ④
          ▼
        模型
          ▲
          │ ⑤
   data/reference/ds3/            ← 静态游戏知识
   items.json · bonfires.json · routes.json
```

四层职责，边界要硬：

| 层 | 只干这件事 | 不许干 |
|---|---|---|
| 解析器 | 字节 → 结构化数据 | 不做「任务完成了吗」这类判断 |
| 封装层 | 进程、错误、缓存 | 不解析格式 |
| 工具层 | 暴露能力、控制上下文体积 | 不藏业务逻辑 |
| 静态知识 | 客观事实（物品、篝火、连通） | 不依赖玩家状态 |

**换游戏只换解析器。** 从 DSR 换到 DS3 时，`state/`、`tools/`、`docs/` 一行没改。

## 2. 存档格式（已实机验证）

### 2.1 容器

`%APPDATA%\DarkSoulsIII\<SteamID>\DS30000.sl2`

- BND4，12 个条目，表头 0x40，条目头 0x20，名字表 UTF-16，数据从 0x300 开始
- 每条目：`[0:16]` = `MD5(data[16:])`、`[16:32]` = IV、`[32:]` = AES-128-CBC/PKCS7
- 密钥 `FD464D695E69A39A10E319A7ACE8B7FA`（公开常量，格式来自 MIT 许可的 DS3SaveUnpacker）
- 条目 0–9 是角色槽，10 是读档界面摘要，11 是索引/联机记录
- 空槽解密后全零

### 2.2 必须是「相对名字」而不是绝对偏移 ⚠️

解密结果**前 4 字节是长度前缀**（等于长度 − 4），去掉后才是 payload。

同一角色两次存档，名字位置从 `0x14148` 变成 `0x13928`——**平移了 0x820**，因为槽内前面的变长区块改了长度。所以：

- 一切字段都按**名字锚点 + 相对偏移**读
- 名字本身靠**结构自校验**扫描定位：前置 8 项属性必须在 1–99、体力 1–99、等级 1–802、且等级不大于属性总和

按固定偏移读会静默返回乱码，且看起来像解密失败——这是本项目踩过最贵的坑。

### 2.3 字段表（相对名字）

| 偏移 | 内容 |
|---|---|
| `-0x44` | 8 × u32：VIG ATN END STR DEX INT FTH LCK |
| `-0x1C` | u32：VIT（体力单独存放，不在上面那串里） |
| `-0x18` | u32：等级 |
| `-0x14` | u32：持有灵魂 |
| `+0x00` | 16 × UTF-16LE：角色名 |
| `+492` / `+496` | 左手 / 右手武器 |
| `+540` / `+544` / `+548` / `+552` | 头 / 身 / 手 / 腿 |
| `+556` – `+568` | 戒指 1–4 |
| `+0x3E4` | 背包网格（16 字节记录） |
| `+0x7AA8` | 关键道具网格 |

### 2.4 事件旗标

槽 payload 是一段顺序序列化的结构体：

1. 从 `0x6C` 起是 gaitem 物品注册表，6144 槽，每槽 8 字节；武器/护甲条目额外 52 字节（`handle & 0xF0000000 ∈ {0x8000_0000, 0x9000_0000}`）
2. 之后按固定偏移链走过背包、仓库、姿势表
3. 落到固定 0x33E5E 字节的**旗标段**，其 `+0x5D` 处是内存格式的世界旗标位图

旗标 ID 编码（8 位数字）：

```
flag_id = 系统位 × 10^7 + 地图码 × 1000 + 局部号
系统位：1 = 事件，6 = 物件，7 = 对话
区域原点：1 → 0xF00，6 → 0x1FE00，7 → 0x2A300
每地图块 0x500 字节，u32 小端，bit 31 = 局部号 0
```

> 该机制参考 [mozartdiniz/ds3-advisor](https://github.com/mozartdiniz/ds3-advisor)（**未发布许可证**）。本项目仅采用偏移与编码这些**格式事实**，代码为独立实现；数据表中标注了来源。

### 2.5 引擎物品 ID 的三种编码

| 类别 | 编码特点 |
|---|---|
| 武器 | 基础 ID + 升级等级（0–10），查名要试 +0…+10 |
| 防具 | 装备槽存高字节 0x01，名称表可能用 0x1X，只能取低 3 字节匹配 |
| 戒指 | 装备槽**丢了高字节 0x20**，查表前要补回；+1/+2/+3 是 base+tier |

背包网格里的 ID 反而是完整形式，直接查表即可。

## 3. 数据切片

工具按**切片**返回，而不是一次性倒出整个存档——这是控制上下文的核心手段，也是 `ds3_get_section` 存在的理由。

| 切片 | 内容 | 置信度 |
|---|---|---|
| `character` | 等级、九项属性、持有灵魂 | 已用游戏内面板逐项核对 |
| `progress` | 游戏时长、最后休息的篝火与区域 | 与进度图景自洽 |
| `bosses` | 24 个 Boss 的击败状态 | 用户确认过两个「未击败」 |
| `bonfires` | 69/81 篝火，按区域统计 | 与 Boss 状态三方互证 |
| `equipment` | 当前穿戴的 10 个槽位 | 与属性/流派自洽 |
| `inventory` | 背包计数、关键道具、堆叠前 15 | 关键道具印证了进度 |

**设计原则**：先给「有什么」，再按需取「内容」。DS3 一个角色几千个旗标位，整包导出必爆上下文，而且模型看着 `0x1F2A8` 也说不出话。

## 4. 工具面

| 工具 | 参数 | 作用 |
|---|---|---|
| `ds3_overview` | `save_id?` | **一次调用拿到完整处境**：等级/位置/Boss/六条收集轴/缺哪些戒指法术 |
| `ds3_list_saves` | `fresh?` | 列出角色与可用切片 |

| `ds3_plan_route` | `save_id?`, `from?`, `targets?` | 按连通图排访问顺序 |

**刻意不做的**：任何写存档的工具。见决策点 D2。

### 4.1 工具挂在预设里，不是全局

这是 0.3 的架构决定。若把四个工具与人格段注册到全局，**每个会话**（写代码、查资料）都会背上黑魂3 的工具 schema 和「你是黑魂3 攻略」的人格段——既污染上下文，也让模型在无关任务里选错工具。

因此按 config 拆两半：

| 挂载点 | config | 提供 |
|---|---|---|
| profile 行（本 bundle 第一行） | `tools:false, prompt:false, panel:true` | `/darksouls-guide/progress` 路由、侧栏地图 |
| 预设行 `preset-ds3-guide` | `tools:true, prompt:true, panel:false` | 四个模型工具、人格段、存档上下文 |

`apply()` 用 `config.tools/prompt/panel` 分流，两个挂载点共用一份代码。可验证的结论：当前标准会话的 `listTools` 里**一个 `ds3_` 都没有**，隔离成立。

## 5. 进度轴：从「篝火数」到「还缺什么」

只有篝火数的面板没法用——它回答不了「我还差什么才能全成就」。0.3 加了五条轴，全部**可由存档推导**：

| 轴 | 来源 | 计数方式 |
|---|---|---|
| 篝火 | 事件旗标 → `bonfires.json` | 74/78 |
| 戒指 | 背包 ID ∩ `items.json.ring` | **按家族计**，+1/+2/+3 不算新戒指：37/74 |
| 魔法 / 咒术 / 奇迹 | 背包 ID 落在 `good` 的三个 ID 区间 | 5/38、5/32、8/38 |
| 誓约 | `ring` 表里 `5368809xx` 段 | 1/8 |

三个必须讲清的口径问题：

1. **戒指按家族计，不按条目计。** 表里 116 个戒指条目里有大量 +1/+2/+3 变体；按条目算会把「拿到 +3 就等于拿了三个」变成假进度。去后缀归族后是 74 个家族，更接近玩家心智，也避免同一枚戒指被重复计数。另附 `tierUpgrades`（已有低阶、还能升到高阶的戒指），这才是 NG+ 真正要做的事。
2. **法术表 108 条无重复。** 先按 `1074xxx/1076xxx/1077xxx` 区间分魔法/咒术/奇迹，再用「去后缀归一化」检查过撞名——0 条重名，所以不需要去重逻辑。
3. **`The First Flame` 是结局分支标记，不是漏掉的篝火。** 面板与工具都显式标注，不把它算作缺口。

「拥有」的唯一证据是**背包里在**。DS3 没有收集检查表，卖出/丢掉的物品会真的消失，这是数据本身的性质，不是实现缺陷。

## 5.1 可达性：从「缺 35 枚」到「这 10 个现在就能换」

缺口数量本身不构成决策。同一个「还差 8 个」可能是「去灵魂交换处走一趟」，也可能是「再刷八枚誓约道具」。0.3 把缺口分成四类，**每一类都必须有存档或参考表里的证据**：

| 类别 | 判定依据 | 例子 |
|---|---|---|
| `now` | Boss 旗标已置位 + 灵魂还在包里 | 10 个未交换的 Boss 灵魂 |
| `now` | 篝火旗标未置位 + 区域已知 | 伊鲁席尔 2 个 |
| `covenant` | 缺口物品在教团奖励表里 | 5 个奇迹锁在教团等级 |
| `ngPlus` | 参考表里该戒指**没有基础款** | 修完名字后为 0 |
| `unknown` | 证据不足 | 一律如实报，不猜 |

**教团进度是可算的**，因为存档里存着誓约道具的数量：

```
Warrior of Sunlight   Sunlight Medal 2/10   还差 8
Blade of the Darkmoon Proof of a Concord Kept 2/10  还差 8
Aldrich Faithful      Human Dregs 1/10      还差 9
```

这比「去刷教团」有用得多——它把「刷」变成了一个具体数字。而且只对**已持有至少一枚**的教团报告，没碰过的教团不列，避免列出一堆无意义的 0/10。

**顺带修掉的上游数据错误。** `items.json` 里有三个戒指名字被截断（`Havel +3 DLC` 而非 `Havel's Ring +3 DLC`），按名字归族会造出**三个永远无法完成的「幽灵家族」**。修正后戒指总数从 74 变 71，`ngPlus` 从 2 变 0——原来那 2 个是我自己的数据 bug 造出来的假象。已在 `_source` 字段记录这处修正。

## 6. 路线规划

`data/reference/ds3/routes.json` 存 19 条区域边（双向），每条带 `note` / `requires` / `confidence`。

### 6.1 传送改变了一切（0.4 修正）

最初把「跳数」当作路线成本，结果算出一份通关存档「去绘画世界要 5 跳步行」——**这是错的**。

DS3 里篝火就是传送点。19 个区域里 18 个已点亮篝火，意味着「从 A 到 B」绝大多数情况是在菜单里选一下，不是走连通图。

修正后的规则：

| 目标区域状态 | 运输方式 | 成本 |
|---|---|---|
| 已点亮篝火 | `warp` | 0 跳，不需要连通路径 |
| 无篝火（未探索） | `walk` | 按连通图算跳数，附带 `requires` |

`requires` 与 `uncertain` 只在 `walk` 时才有意义——传送不需要「小人偶」或「古龙姿势」。

**教训**：连通图是对的，但它描述的是**空间相邻**，不是**实际代价**。任何「最短路径」都得先问清楚成本函数是什么，否则算得再准也是错的。

`data/reference/ds3/routes.json` 存 19 条区域边（双向），每条带 `note` / `requires` / `confidence`。

算法要点：

- **穷举全排列**而非最近优先贪心。目标 ≤ 8 个时直接算最优；贪心会把远处的点留到最后，把整条路线拖长（实测多绕 3 跳）
- 目标默认取「还有未点亮篝火的区域」
- `requires` 只从**正向边**收集——回头路上的「触碰画作」没有意义，会误导模型
- `confidence: medium` 的路段在输出里显式标注「存疑路段」

## 6.5 成就清单：只报能验证的

成就清单最容易变成谎言。DS3 有几十个成就，但**存档能证明的只有少数**，剩下的靠猜就会给出「你 92% 了」这种编造的数字。

实测结论（不是推测）：

| 成就类 | 能否验证 | 依据 |
|---|---|---|
| 全 Boss 击败 | ✅ | 24 个 Boss 旗标 |
| 全部 15 种质变宝石 | ✅ | 背包物品 ID |
| 加入全部 8 个誓约 | ✅ | 誓约徽章在戒指表段 |
| 全部 108 个法术 | ✅ | 按三系 ID 区间 |
| 全部戒指 | ✅ | 按家族计 |
| 全部姿势 | ❌ | **布局里那个「计数」后面跟的是物品 ID 表**（400101、300001…），不是姿势列表 |
| 誓约等级 | ❌ | 只记当前持有道具，不记已上交数量 |
| 元素瓶上限 | ❌ | 碎片拾取即消耗，无计数器 |
| 全部结局 | ❌ | 分支选择，不进旗标 |

所以输出里 5 项带进度条，4 项只列名字并写明为什么读不出。**提示词里也明确写了「不要估算这些」**，防止模型自己补一个数字上去。

这一条比多覆盖几个成就重要：**面板上出现一个假的 92%，比出现「读不出」糟糕得多。**

## 8.1 可视化面板（Client 半）

一个地图式进度看板，挂在 **`main` 槽**（左侧栏条目选中的中央面板）。

### 需要写对的三件事（都是踩坑得到的）

1. **`inject` 决定服务可见性，不是加载顺序。** 没在 `inject` 里声明 `webServer`，`ctx.get('webServer')` 返回 `undefined` 且**不报错**——路由被 `if (server)` 静默跳过，表现为 404。声明后立刻正常。
2. **客户端模块不会热重载。** Host 侧改代码会 HMR，但 `client.js` 的改动必须**完全退出应用**才重新扫描模块表。
3. **左侧栏入口 = `sidebar.panellist` + `main` 一对**，两者的 `id` / `key` 必须同值。参考 `dsh-context` 的实现。

### 数据流

```
存档 → dump_save.py → run.js → index.js 的 /darksouls-guide/progress
                                              ↓ fetch（60 秒轮询）
                                        client.js 渲染 SVG
```

**401 vs 404 是有效的区分**：401 是认证拦截（请求到了服务器），404 是路由没注册（插件侧问题）。

### 布局的诚实说明

`NODES` 里的 `[列, 行]` 是**按推进顺序手工排布**的，不是地图坐标。存档只记录「你在哪个篝火」，区域的 x/y/z 在游戏加密封包里，拿不到。所以这是**区域连通关系图**，不是能指路的地图。

`NODES` 的 key 必须与 `bonfires.json` 里的区域前缀完全一致——上一版残留了「菲莲诺尔寝室」「初始之火」两个不存在的节点，永远显示「无数据」。已用脚本交叉校验：19 个节点 = 19 个区域。

| 1 | `ctx.sidebarRightTabs.register({ id, kind, title, guide })` | 缺 `guide`，没有任何入口能打开它 |
| 2 | body 用 `{ name: 'sidebar.right.pane.tab', key: <definition.id> }` | 对（key 必须是 **id**，不是 kind） |
| 3 | title 用 `{ name: 'sidebar.right.pane.tab.title', key: <definition.id> }` | 注册了但 key 不对 |
| 4 | `package.json` → `dsh.client.inject` 含 `@deepseek-ai/dsh-client-ui-sidebar-right` | 缺；已补 |

`title` 的签名是 `title(address)`——会被传入正在打开的地址，不是无参。`guide: [{ order, title, description, icon }]` 决定它在右侧栏启动页上有没有卡片。

**参考实现是 `dsh-context`**（`node_modules/dsh-context/lib/client.js` 未压缩、可读），它走的是完全相同的公开路径。这个 seat 的准确文档在 asar 里 `@deepseek-ai/dsh-client-ui-sidebar-right` 的 README「Extension seats」一节，比任何试错都可靠。

教训：**先前是靠猜 API 和反复重启定位的，而答案就在同一台机器上的一个可读插件里。** 遇到「某个 seat 注册不上」时，先找已经注册成功的同类插件读它的实现，再动手。

### 8.2 输入框里的进度药丸（`conversation.input.left`）

日常交互的主路径不是面板，而是**输入框工具栏左侧那颗药丸**：`Lv103 · 传火祭祀场`。点开是一个 236px 的小面板，里面是六条进度轴和四个快捷提问芯片。

| 芯片 | 写入草稿的问题 |
|---|---|
| 下一步干嘛 | 我现在该去哪儿？ |
| 还缺什么 | 我全收集的话还缺什么？按能补的数量排一下。 |
| 配装建议 | 按我现在的属性和装备，怎么调整比较好？ |
| 加点 | 我接下来该往哪个方向加点？ |

**为什么不放在输入框下方。** 最初做在 `conversation.composer.dock` 里，是整条状态带，效果是每个会话下方**永久多出一行**——信息是对的，代价是长期的垂直空间。改成工具栏里的一颗药丸后行高完全不变（22px，与相邻控件同高），信息在点击时才出现。**凡是「每轮都在但并非每轮都看」的信息，都应该收进弹层。**

三个实现要点：

1. **写草稿要用 `inputActions.insertText(text, span)`，不是 `setDraft`。** `insertText` 插入的是可撤销的纯文本编辑，玩家手打的内容不会被抹掉；`setDraft` 会整段替换草稿。`span` 由 `captureInsertion()` 取得，其中 `draftRev` 用于防止在草稿已被改动时插入（编辑器拒绝时返回 `false`，此时才退回 `setDraft`）。
2. **读不到存档时药丸直接不渲染（返回 `null`）。** 否则每个会话的工具栏里永远挂一个失效控件。存档问题应该在面板里暴露一次，而不是在每个会话里反复提醒。
3. **弹层要处理外部点击关闭。** 工具栏空间窄，弹层是绝对定位的覆盖层，不关闭会挡住编辑器。

### 8.3 系统提示词：作用域是重点

提示词由两段组成，**都注册在预设作用域内，从不全局注册**：

| 段 | 内容 | 性质 |
|---|---|---|
| `darksouls:persona`（section） | 「你是某个具体玩家的黑魂3 攻略」+ 工作方式 | 静态，进可缓存前缀 |
| `darksouls:state`（context） | 每步重算的存档实况 | 动态，15 秒缓存 |

三个必须遵守的约束：

1. **必须是预设作用域。** 全局注册会让写代码的会话也变成黑魂3 助手。已验证：标准会话的 `listTools` 里没有任何 `ds3_*`。
2. **`context` 的 provider 不能抛异常。** 它每一步都跑；存档损坏、读不到角色、Python 缺失，都只能退化成一行诚实的说明，不能打断请求。
3. **必须是快的。** provider 每次组装都执行，由 15 秒缓存 + 后台刷新兜住——这直接把「解析器要 4.2 秒」变成了架构问题，见 §10 性能一节。

## 10. 已知局限

### 性能：一条从前不可见的架构约束

`find_character` 原本扫描 786k 个偏移逐个试 UTF-16 解码，单次解析 **4.2 秒**。在只有工具调用时才跑时这不是问题；**一旦系统提示词的 context provider 每步都要读存档，它就变成了架构问题**。

两处修复，合计 **4.2 s → 288 ms**（14×）：

| 问题 | 修复 |
|---|---|
| 每字符一次迭代扫描 | 用正则 `(?:[\x20-\x7e]\x00)+` 先筛出候选串，只在候选起点上验证 |
| 9 个空槽每个仍走完慢路径（0.32 s ×9） | 空槽是全零，`p.strip(b"\x00")` 为空则直接返回 |

第二条是关键：正则只解决了「有名字的槽」，真正的大头是**九个空槽各自跑完整扫描**。修复后输出与修复前逐字段一致（含 24 Boss、74 篝火、91 武器、370 个 ownedIds）。

其余局限：

1. **Boss 表只有 24 条**，覆盖主线与 DLC 主要 Boss，不含所有小 Boss
2. **`routes.json` 是手写草稿**，2 条边标 medium，全部未经实走验证；且**没有区域内导航**（走哪个门、房间顺序）
3. **装备只读当前穿戴**，不区分背包里是否有同名物品
4. **22 件背包装备无名称映射**（名称表覆盖不全），显示为 `未知 0x...`
5. **NPC 任务线不可用**（见 M4）
6. **仅 Windows + 仅 PC 未加密存档**；PS4 `.sl2` 需先解密
7. **不写存档**，也不预览/校验写回后的校验和
8. **收集轴只覆盖「可验证」的部分**：戒指/法术/誓约按背包判定，但**没有全成就清单**——「全成就」还包含动作、姿势、强化上限等存档里读不出完整状态的项，这些不做承诺

## 11. 决策点

### D1. 解析器跨语言
当前：Node `child_process` 调 Python，需要 Python 3 + `cryptography`。
备选：纯 JS 重写（`node:crypto` 能做 AES-CBC，但要重新实现容器与全部偏移并重验）。
**结论：先保持 Python**，等分发需求明确再评估。

### D2. 写不写存档
**只读。** 写回要重算 MD5 与 AES，且在线模式有封禁风险。若将来要做，必须独立工具 + 显式确认 + 自动备份，默认关闭。

### D3. 知识来源
**本地优先。** 客观数据进 `data/reference/`，攻略的「话术」交给模型。不联网拉 wiki 正文。

## 11.5 开源发布边界

仓库公开发布，但有四类内容**永远不进版本库**：

| 内容 | 原因 |
|---|---|
| `*.sl2` 存档 | 含 Steam 账号 ID、角色名、完整游玩记录 |
| `*.vdf` | Steam 云同步元数据，里面就是 account id |
| `ref/` | 第三方源码，**无授权文件**，不可再分发 |
| `archive/` | DSR 时代遗留：无来源数据、失去依赖的旧解析器 |

`.gitignore` 用通配而不是逐个目录列，因为最初只写了 `tests/fixtures/saves/`，结果 `tests/fixtures/ds3/` 下 4 个 9MB 存档一个都没被排除。

`items.json` 的来源在 `_source` 里如实写明：上游 `ds3-advisor` **声明无授权**，本仓库只复现事实性游戏数据（数字 ID 与游戏内显示名），不含任何源码、游戏二进制或资源文件。LICENSE 里也单列了这一点。

### 0.3 版本的架构教训
- **功能做进全局注册表之前，先问「这个对话需要它吗」。** 工具 schema 和人格段每轮都进上下文，代价是长期的；预设作用域让代价只落在选了它的会话上。
- **性能在「每步都跑」的路径上才暴露。** 同一个 4.2 秒，在「点了才跑」和「每步都跑」的差别，是能不能用。
- **百分比不是进度，缺口才是。** `37/74` 能推出「还差 37 枚」，`50%` 不能。所有轴都报分数，不报百分比。
